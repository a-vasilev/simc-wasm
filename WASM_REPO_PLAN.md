# simc-wasm — Engine-Fork Repo Plan (v0.1)

Detailed implementation plan **scoped to this repository only** (the simc fork,
repo #1 in `OVERALL_PLAN.md` §4). The `web`, `data`, and `api` repos are out of
scope here. This document plans; it does not implement.

## 0. What this repo is responsible for

This repo's job, per the overall plan (§4, §5, §10–11):

- Carry a **small, rebase-friendly delta** on top of upstream simc that makes the
  `engine/` CLI compile to a **threaded, SIMD WebAssembly** artifact via Emscripten.
- Provide a **build** (local + CI) that produces `simc.wasm` + ES6 JS glue.
- Provide **CI** that builds the artifact, runs a **validation diff vs native simc**
  to catch porting regressions, and publishes the artifact as **GitHub Release
  assets** for the `web` repo to consume.

It covers **Phase 0 (spine)** and the **engine half of v1**. The React app, item
DB, and loot pipeline live in other repos.

### Decisions locked (from planning Q&A)

1. **Git topology:** add `upstream`, pin current `midnight` HEAD as the base, do all
   WASM work on a `wasm` branch, rebase per patch.
2. **Build layout:** new top-level `wasm/` directory holds the Emscripten build +
   config; existing CMake is touched only with minimal `if(EMSCRIPTEN)` guards;
   engine sources only with `#ifdef __EMSCRIPTEN__` where genuinely forced.
3. **Artifact delivery:** GitHub Release assets (versioned, pinned to base SHA).
4. **CI scope:** new separate `.github/workflows/wasm.yml`; existing native CI
   (`main.yml`/`build.yml`/spec tests) left untouched.

## 1. Findings that ground this plan (verified in the tree)

- **Build options already exist.** `CMakeLists.txt` and `engine/CMakeLists.txt`
  expose `BUILD_GUI`, `SC_NO_THREADING`, `SC_NO_NETWORKING`. The `simc` CLI target
  is `add_executable(simc engine/sc_main.cpp)` linked to the `engine` library.
- **Source lists are explicit, not globbed.** `source_files/cmake_engine.txt`
  (`set(source_files …)`, 364 entries, generated by `source_files/synchronize.py`).
  → The plan's "CMake file-globbing needs handling" concern (§5) **does not apply**;
  no source-list surgery is needed for the wasm target.
- **Networking is cleanly removable.** With `-DSC_NO_NETWORKING=ON`, curl/wininet
  linkage is skipped and `http::cache_load/save` + `bcp_api::token_*` become stubs
  (`engine/interfaces/sc_http.cpp:22`, guards across report/sim/util). So the
  unconditional calls in `sim_t::main` (`engine/sc_main.cpp:261`) are safe.
- **Threading is `std::thread`** in `engine/util/concurrency.cpp` — kept, built with
  Emscripten `-pthread` (no stubbing, unlike the 2018 port).
- **CI is reusable-workflow style** (`.github/workflows/main.yml` → `build.yml`),
  ccache + ninja; `profiles/CI.simc` exists as a ready validation profile.
- **Likely engine deltas (anticipated, confirm in Phase 0):**
  - `config.hpp:32` defines `SC_SIGACTION` for **all** non-Windows builds → it
    switches on under Emscripten; the POSIX signal handler in `sc_main.cpp` may need
    an `__EMSCRIPTEN__` guard.
  - `concurrency.cpp` `computer_process::set_priority` uses `setpriority` on the
    `__unix__` path (musl stub under emcc) — candidate no-op guard.
  - `get_cache_directory()` (`sc_main.cpp:168`) — harmless under `SC_NO_NETWORKING`
    but lives in MEMFS; confirm.
- **Git state:** `origin = a-vasilev/simc-wasm`, branch `midnight`, **no `upstream`,
  no `wasm` branch**; the WASM delta exists nowhere yet (greenfield).

## 2. Git model: the two kinds of ref (important)

Upstream simc **does not tag releases** — retail data lands as a continuous commit
stream on `midnight`. So we keep two clearly separated concepts; do **not** conflate
them (the v0.1 draft did):

| Concept | What it is | Where it points | Purpose |
|---|---|---|---|
| **Upstream pin** | A commit **SHA** on simc's `midnight` branch | an *upstream* commit | The rebase target + reproducibility record. **Not a release.** Recorded in a tracked file `wasm/BASE_SHA`, not as the release tag. |
| **Release tag** | `v<major>.<minor>[-N]` (e.g. `v1205.01`) | **our `wasm` HEAD** (delta *on top of* the pinned SHA) | What CI builds + publishes, and what the `web` app pins to. |

The release tag must sit on **our `wasm` tip**, never on the bare upstream commit —
the artifact is built from our delta-applied tree, not from raw upstream.

### Release tag scheme (decided)

`v<SC_MAJOR>.<SC_MINOR>` derived from `engine/config.hpp` (`SC_VERSION`, currently
`1205-01` → `v1205.01`). Because simc keeps committing within a single WoW patch, a
**re-rebase onto a newer SHA at the same `SC_VERSION`** gets a numeric suffix:

```
v1205.01      -> base <sha-a>   (first release on simc 1205-01)
v1205.01-2    -> base <sha-b>   (re-rebased later in the same patch)
v1205.01-3    -> base <sha-c>   ( ...again)
v1206.01      -> base <sha-d>   (simc bumped version -> new patch)
```

Tags are **annotated** (carry tagger/date/message). The "which suffix" rule: if
`v<ver>` already exists, use `-2`, then `-3`, … (check `git tag --list 'v1205.01*'`).

### One-time setup

```bash
git remote add upstream https://github.com/simulationcraft/simc
git fetch upstream
git switch -c wasm <current-midnight-HEAD-sha>   # all WASM delta lives here
# add the WASM delta commits, including a tracked wasm/BASE_SHA recording the pin:
echo <current-midnight-HEAD-sha> > wasm/BASE_SHA
git push -u origin wasm
```

- Keep the WASM delta as **a few logical commits** on `wasm` (e.g. "build: wasm
  target", "engine: emscripten platform guards", "ci: wasm build + validation",
  "pin: BASE_SHA").
- **Rebase, never merge** onto new bases so history stays "N commits on base SHA X".
- `wasm/BASE_SHA` is the durable, diffable source of truth for the pin (CI reads it
  into `manifest.json`); the `data`/`web` repos pin the **release tag**, satisfying
  the `data patch == engine patch` rule (§4).

## 3. Repository layout additions

Everything new is contained; in-place edits are minimal.

```
wasm/
  README.md            # prereqs, pinned emsdk version, how to build & run locally,
                       #   current base SHA / version
  build.sh             # emcmake cmake … (flags) + ninja + wasm-opt; the canonical build
  emscripten.cmake     # CMake include holding the emcc compile/link flags (kept out of
                       #   the upstream CMakeLists to minimize in-place delta)
  smoke/
    run_smoke.mjs      # Node ESM harness: load module, write a .simc to MEMFS,
                       #   callMain([... json2=out.json]), read out.json, assert DPS>0
    quick.simc         # tiny single-actor profile for the smoke/Node run
.github/workflows/
  wasm.yml             # build + validation diff + release (new, separate)
```

In-place edits (small, guarded):

- **`CMakeLists.txt`** — one `if(EMSCRIPTEN)` block: force `BUILD_GUI=OFF`,
  `BUILD_TESTING=OFF`, `SC_NO_NETWORKING=ON`; `include(wasm/emscripten.cmake)`;
  apply emcc **link** options to the `simc` target via `target_link_options`.
- **`engine/CMakeLists.txt`** — at most ensure `-pthread` reaches engine compile
  under EMSCRIPTEN (likely already fine via `find_package(Threads)` +
  `THREADS_PREFER_PTHREAD_FLAG`; confirm, add guard only if needed).
- **Engine sources** — only `#ifdef __EMSCRIPTEN__` guards proven necessary in
  Phase 0 (candidates in §1). Goal: **zero or a handful of lines.**

## 4. Build system changes (detail)

### 4.1 Configure-time (`if(EMSCRIPTEN)` in top-level CMakeLists.txt)

| Setting | Value under EMSCRIPTEN | Why |
|---|---|---|
| `BUILD_GUI` | OFF | No Qt in browser (§5: build only `engine/`). |
| `SC_NO_NETWORKING` | ON | No curl/wininet; Armory import is not in v1 (§3, §11). |
| `SC_NO_THREADING` | **OFF** | We keep real threads (browser pthreads). |
| `BUILD_TESTING` | OFF | CTest harness (`tests/run.py`) is Python/subprocess-driven; replaced by the Node smoke + CI validation diff. |

### 4.2 Compile/link flags (`wasm/emscripten.cmake`, applied to `simc` + `engine`)

Per overall plan §5; split into compile vs link:

**Compile (`-pthread -msimd128 -fwasm-exceptions -O3`)** on both `engine` and `simc`
targets (threading + exceptions must match at compile and link).

**Link (`target_link_options(simc …)`):**

- `-pthread`, `-sPTHREAD_POOL_SIZE=…` (sized at runtime to
  `navigator.hardwareConcurrency`; see note below), `-sPROXY_TO_PTHREAD`
- `-fwasm-exceptions`
- `-sALLOW_MEMORY_GROWTH=1` (start here; consider sized `INITIAL_MEMORY` after
  measuring)
- `-sMODULARIZE=1 -sEXPORT_ES6=1 -sEXPORT_NAME=createSimc`
- `-sENVIRONMENT=web,worker`
- `-sINVOKE_RUN=0 -sEXIT_RUNTIME=0` + `-sEXPORTED_RUNTIME_METHODS=['callMain','FS']`
  so the app drives the CLI `main()` repeatedly via `callMain` and reads MEMFS.
- `-O3` + `wasm-opt` pass for release; symbol stripping.

**Pool sizing note:** `PTHREAD_POOL_SIZE` is fixed at link time. Options to resolve
with the `web` repo (flag here, decided there): build a generous fixed pool, or use
`-sPTHREAD_POOL_SIZE_STRICT=0` + on-demand thread spawn. Default for v1: a fixed pool
sized to a sane max (e.g. 8) plus memory growth; revisit. **Open item O3 (§10).**

### 4.3 Driving the binary (no embind, per §5)

1. App (web repo) writes the user profile + options to `/in.simc` in **MEMFS**.
2. `callMain(['/in.simc', 'json2=/out.json', ...options])`.
3. Read `/out.json` from MEMFS — simc's native JSON report is the render input.

This repo only needs to **prove** that path via `wasm/smoke/run_smoke.mjs` under
Node; the app-side wiring is the `web` repo's job.

## 5. Anticipated engine-source delta (keep tiny; confirm empirically)

Discover during Phase 0 by iterating the build. Anticipated candidates, each a
1–few line `#ifdef __EMSCRIPTEN__` guard:

1. **Signal handling** — guard `SC_SIGACTION` off for Emscripten (in `config.hpp`)
   *or* leave it if `sigaction` links cleanly; decide by build result.
2. **`set_priority`** — no-op under `__EMSCRIPTEN__` in `concurrency.cpp` if
   `setpriority` is unavailable/ineffective.
3. **Locale** — `std::locale::global(std::locale("C"))` in `main()` is fine; watch
   for any other locale use that emcc's libc++ rejects.
4. **Filesystem/cache pathing** — only if `get_cache_directory()` misbehaves under
   MEMFS (expected fine with networking off).

**Acceptance:** the delta stays small enough that a per-patch `git rebase` is a quick,
low-conflict operation. If the delta grows, that's a signal to push a change upstream
or rethink, not to carry a large patch.

## 6. CI — `.github/workflows/wasm.yml` (new, separate)

**Triggers:**
- `push` to `wasm` → run Job A (build) + Job B (validation diff) as a **CI gate**.
  **No release.** (Fires on every rebase force-push, validating before you tag.)
- `push` of a tag matching `v*` → run A + B, then Job C (**publish Release**).
- `workflow_dispatch`; optionally `pull_request` targeting `wasm`.

**Job A — build:**
1. `actions/checkout` (full history; needs base SHA for the git-rev define).
2. Set up pinned Emscripten (`mymindstorm/setup-emsdk` or the `emscripten/emsdk`
   container) — **pin the emsdk version** in `wasm/README.md` and the workflow.
3. ccache (mirror existing `build.yml` caching).
4. `emcmake cmake` configure + `ninja` + `wasm-opt` (via `wasm/build.sh`).
5. Upload `simc.wasm` + `simc.js` (+ any `.worker.js`) as a workflow artifact.

**Job B — validation diff vs native (the regression guard, §5):**
1. Build (or fetch) a **native** simc from the **same source tree/SHA**.
2. Run a battery of profiles (start with `profiles/CI.simc`; expand to a handful of
   per-spec profiles) under **both** native and the wasm build (wasm via Node +
   `callMain`), each with a **fixed seed + fixed iterations** for determinism.
3. Parse `json2` DPS for each profile; **fail if any |Δ| exceeds tolerance**.
   - Cross-compiler FP differences mean exact match is unrealistic → use a
     **relative tolerance** (default **0.5%**, configurable). **Open item O4 (§10).**
4. Emit a summary table (profile, native DPS, wasm DPS, Δ%) to the job log.

**Job C — release (only on a `v*` tag, after A+B green):**
- Create a GitHub Release for the tag (built from `wasm` HEAD that the tag points
  at); attach `simc.wasm`, `simc.js`, `.worker.js`, and a small `manifest.json`
  (**upstream base SHA from `wasm/BASE_SHA`**, sim `SC_VERSION`, the release tag,
  emsdk version, build flags, file hashes). Use the upstream patch identity in the
  **Release title** (e.g. "simc 1205-01 — base `<sha>`"). The `web`/`data` repos pin
  the tag.

**Threads in CI/Node:** Node needs `--experimental-wasm-threads`/appropriate flags
and SharedArrayBuffer; verify the validation run actually uses >1 thread or pin
`threads=1` for the deterministic diff and assert multicore separately.

## 7. Release / artifact contract (for the `web` repo)

- **Versioning rule (§4): `data patch == engine patch`.** Releases are tagged
  `v<SC_MAJOR>.<SC_MINOR>[-N]` on `wasm` HEAD (§2); `web`/`data` pin the same tag so
  all three move together. The upstream base SHA travels in `manifest.json`, not the
  tag.
- **Assets:** `simc.wasm`, `simc.js` (ES6, `EXPORT_NAME=createSimc`), optional
  `.worker.js`, `manifest.json`.
- **Consumption model:** app `import createSimc from 'simc.js'` in a Web Worker,
  COOP/COEP set by the host (web repo concern). This repo guarantees the module
  **runs `main()` via `callMain` and reads/writes MEMFS** — the documented interface.

## 8. Per-patch update runbook (recurring; goes in `wasm/README.md`)

When a new WoW patch (or a fix you want) lands as upstream commits, **you decide**
when to rebase onto one of them; the rebase + tag is what cuts a new web-consumable
release.

```bash
git fetch upstream
# 1. pick a newer base on the retail branch (prefer a data-update-live-* point)
NEW_SHA=<chosen-upstream-sha>

# 2. rebase our delta onto it (plain rebase for patch->patch)
git rebase "$NEW_SHA" wasm       # resolve the (small) conflicts in wasm/ guards

# 3. record the new pin in the tracked file and amend the pin commit
echo "$NEW_SHA" > wasm/BASE_SHA
git add wasm/BASE_SHA && git commit --fixup <pin-commit>   # or amend the pin commit

# 4. push the branch -> triggers the CI gate (build + validation diff, no release)
git push --force-with-lease origin wasm

# 5. once green, tag wasm HEAD with the release version -> triggers the Release.
#    derive v<MAJOR>.<MINOR> from engine/config.hpp SC_VERSION; add -N if it exists.
git tag -a v1205.01 -m "simc 1205-01 @ $NEW_SHA"   # or v1205.01-2 if v1205.01 exists
git push origin v1205.01
```

- The **release tag points at our `wasm` HEAD**, not at `$NEW_SHA` (§2).
- **Yearly expansion switch only:** `git rebase --onto <new-expansion-sha>
  <old-base-sha> wasm` (§4).
- If a pinned SHA lands mid-data-update and fails the validation sims, **bump to a
  slightly later commit** and re-tag (§4).

## 9. Work sequence & acceptance (this repo)

Maps to overall-plan Phase 0 + engine-half of v1.

- **M0 — Git scaffolding.** `upstream` remote, `wasm` branch off the pinned SHA,
  `wasm/BASE_SHA` recorded. *Done when the branch exists and the pin is committed.*
- **M1 — Local trivial build.** `wasm/build.sh` produces `simc.wasm` from a clean
  `emcmake` configure; a **trivial sim runs under Node** (`run_smoke.mjs`) emitting
  `out.json`. Engine delta minimized. *Done when Node prints a DPS > 0 from a pasted
  profile.* (Plan §11 step 1–2.)
- **M2 — Threaded build.** Same, with `-pthread`/`PROXY_TO_PTHREAD` and a real
  multi-actor/iteration sim; confirm threads active (pool spins up). *Done when a
  multi-thread run completes and matches a single-thread run within tolerance.*
- **M3 — CI build.** `wasm.yml` Job A green on push to `wasm`; artifact uploaded.
- **M4 — Validation diff.** Job B green: wasm vs native DPS within tolerance across
  the profile battery. *This is the "update = green checkmark" guarantee (§5).*
- **M5 — Release.** Job C publishes a tagged Release with assets + manifest; the
  `web` repo can fetch and pin it.

(Cross-origin isolation, the React app, paste box, and report render are **web-repo**
milestones — not here.)

## 10. Remaining open items (track; not blocking the plan)

- **O1 — Exact engine delta.** Discover empirically in M1 (§5). Expect tiny.
- **O2 — First-load binary size.** Measure after M2 before optimizing (§5, §12).
  Plan: `-O3`/`wasm-opt`/strip first; data-splitting only if first-load is a real
  problem.
- **O3 — Thread pool sizing strategy.** Fixed `PTHREAD_POOL_SIZE` vs on-demand spawn;
  finalize with the `web` repo since it owns `hardwareConcurrency` at runtime (§4.2).
- **O4 — Validation tolerance + profile set.** Default 0.5% relative on
  `profiles/CI.simc`; expand the profile battery and tune tolerance with seed/iteration
  determinism (§6).
- **O5 — emsdk version pin.** Choose and pin a specific emsdk release; record in
  `wasm/README.md` and `wasm.yml`.
- **O6 — `wasm32-wasi` back-pocket build (§5/§9 of overall plan).** Not for v1; just
  don't architect anything in `wasm/` that precludes a future parallel target.
